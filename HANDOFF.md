## 1. What this is

A point-of-sale, billing, inventory and GST records app for a single shop —
currently set up as **Vyapara Bakery Supplies**, a wholesaler selling baking
ingredients to bakeries on cash, UPI and credit.

- **Front end:** React 19, Vite 6, Tailwind 4, Zustand, React Router 6, Recharts, react-to-print
- **Back end:** Express 4 + better-sqlite3 (WAL), in one process (`server.ts`), JWT auth, bcrypt
- **Heavy reads** (reports, dashboard, passbook) run on a worker-thread pool (`db/asyncRead.ts`)
- **Developed and tested on Node 25.2.1**

## 2. Running and testing

```bash
npm install
npm run dev          # development, with hot reload (no build needed)
npm run build        # front-end bundle into dist/
npm start            # production mode: serves dist/ + API on http://127.0.0.1:3000
npm test             # build, then the full suite (~1.5–2.5 min)
npm run test:only    # the suite without rebuilding
npm run lint         # TypeScript type check
```

The tests **never touch `pos.db`**: each file boots the real `server.ts` as a
child process against a throwaway database (`DB_PATH`), and drives it over
HTTP. They run one file at a time on purpose.

### 4.2 Full-screen option

Button in the top bar and on the sign-in screen; **Ctrl/Cmd+Shift+F**; state
follows the browser (Esc, F11); black-backdrop CSS fix; hidden where the
browser has no Fullscreen API (iPhone Safari). Browsers only grant full screen
from a user gesture, so after a reload it comes back on the next click or key,
not on load. Real kiosk mode (`chrome --kiosk`) documented for a dedicated till.

### 4.3 Customer credit ledger ("when and how much")

New table `customer_credit_entries`: one row per change to a customer's
balance — `opening`, `sale`, `payment`, `adjustment` — with signed amount,
balance before/after, who, when, and a note. Every path that moves a balance
goes through **`recordCreditChange()`** in `server.ts` in one transaction.

Added beyond the literal ask: **Record Payment** (`POST /api/customers/:id/credit-payments`).
Without it the only way to record a repayment was to retype the balance.

**Existing data was backfilled:** the 106 historical credit sales came back
exactly. Repayments made before the upgrade were never recorded anywhere, so
each customer's history closes with **one labelled `adjustment`** covering the
difference. My first version put that as a *negative opening balance*, which
read as the shop owing the customer (−₹10,514.98 for Golden Crust Bakers); it
was moved to the end so balances never go negative. All 14 customers reconcile
exactly to their stored balance.

### 4.4 Customers are known by bakery name

The shop refers to customers by bakery ("Sri Ganesh Bakery"), not the owner's
name. Now the **bakery/shop name is the customer's identity everywhere**
(billing picker, customer cards, history, reports, CSV, invoice "Bill To" with
an *Attn:* line) and the person is shown beneath as the contact. A customer
with no shop is shown by their own name.

Validation flipped: previously the person's name was required and the shop
optional. Now a customer needs **either** (plus phone). Lists sort by bakery.
Typing an unknown name in the billing picker pre-fills the *bakery* field, with
a one-click "no bakery? use as the customer's name". One rule, two places:
`customerDisplayName()` in `src/lib/customer.ts` and `CUSTOMER_DISPLAY_SQL` in
`server.ts`.

### 4.5 Customer passbook

**Customers → Passbook** (or click the bakery name) opens `/customers/:id`:
every bill however it was paid, every repayment, correction and opening
balance, with *Billed*, *Received* and *Balance due* after each line. Click a
bill to see its items. Period presets (30 days, 3 months, this year, all time,
custom), newest/oldest first, summary cards, *Balance brought forward*, and
Record Payment on the same page. Replaced the earlier credit-only popup.

Verified on the real data: all 512 customer bills appear (the old view showed
only the ~106 credit sales) and every customer's passbook ends exactly on their

### 4.6 Printing no longer leaves you out of full screen

Chrome always leaves full screen to show its print dialog; a page cannot stop
that. `src/hooks/usePrint.ts` (a wrapper around `useReactToPrint`) notices when
a print caused the exit and restores full screen — immediately if the browser
still counts the click that started the print, otherwise on the next tap or
key press (which still does its normal job). Pressing Esc on purpose is
remembered as a choice and not undone. With `chrome --kiosk --kiosk-printing`
there is no print dialog at all (documented in the README).

### 4.7 FIFO stock: items created in purchases, priced per batch

Asked for: *create items in purchase, set the selling price and profit % there,
bill first-in first-out (last week's ₹85 yeast before this week's ₹90, at its
own price) with the price editable, and manage stock cleanly.*

- **Stock is held in batches** (`stock_batches`), one per purchase line, each
  with its own quantity left, cost (before GST) and selling price (with GST).
- **Purchases** set a **selling price** per line (profit % was on screen at
  first; §4.8 moved it to the report download only). **Items are created only by a saved purchase**: a name not in the
  catalogue makes the row a new item, with HSN and a unit dropdown in the row.
  The server creates it inside the purchase's transaction, and there is no
  other create route. Billing's popup, the Items page's "Add New Item", and the
  Purchases popup (which saved the item *before* the purchase, leaving strays
  when a purchase was abandoned) are all gone. Number inputs have no spinner
  arrows app-wide.
- **Billing sells the oldest batch first, at its price.** A sale that runs past
  the old stock becomes two bill lines (e.g. 10 @ ₹107.10 + 2 @ ₹113.40). The
  price was editable at the till at first; §4.9 took that out.
- **The total on screen is the total charged.** The till sends what it showed.
  If another sale used up a batch meanwhile, the server refuses with
  `409 PRICE_CHANGED`, and the till re-prices and shows a notice.
- **Stock moves only through** purchases, sales, and **stock adjustments with a
  reason** (Items → *Stock & prices*: remove oldest-first, or add a batch).
  Admins can also reprice what's left in a batch. The item form no longer sets
  price or stock. `items.stock_quantity`/`price` are a cache written only by
  `syncItemStock()`, so they always equal what the batches hold.
- **Bill math and FIFO are now one shared module**, `src/lib/billMath.ts`, used
  by both the server and the cart. They used to be two copies kept in step by a
  test.
- **Upgrade:** existing stock is rebuilt into batches from purchase history.
  Each item's stock goes to its newest purchases first, which is what FIFO
  would have left on the shelf. Unexplained stock becomes an 'opening' batch
  with unknown cost. Selling prices are unchanged.
- Two bugs fixed on the way. A new item created from the Purchases popup
  silently never landed in its row (the page read a stale list). The demo
  seeder's `--reset` would fail on the newer tables' foreign keys.

### 4.8 Purchase Items table fits; profit % only in the report download; cost before or after GST

Asked for: *fix the horizontal overflow and clipped columns in the Purchase
Items table; don't display profit % — save it in the backend and show it in the
report download; the owner sets the selling price.* Then: *the item column is
too wide; add a cost-after-GST column — the owner fills either cost and the GST,
and the other cost is calculated.*

- **11 columns → 9, fixed widths** (`table-fixed` + `<colgroup>`): Item ·
  HSN · Metric · Qty · Cost before GST · GST · Cost after GST · Selling Price
  (incl. GST) · Amount. Every column has a base width (984 px in all), and a
  wider screen shares the extra out in proportion, so the item name no longer
  takes all the spare width (it was ~45% of a wide table; now ~18%). GST type
  and slab are one dropdown (*No GST*, *GST 5/12/18/28%* = CGST + SGST, *IGST
  5/12/18/28%*). GST amount and line total are one Amount cell (total, with
  "GST Rs. x" beneath). The form's padding drops from 32 px to 24 px below
  1536 px wide.
- **Cost before *or* after GST.** The owner types either; the other is worked
  out from the GST dropdown and shown in grey. Row state keeps the typed figure
  and which one it was (`cost`, `cost_basis`); `costsOf()` derives the other, so
  a GST change moves the untyped box. Worked back from after-GST, the cost
  before GST keeps six decimals so the line totals exactly (₹100 incl. 18% × 10
  = ₹1,000.00); the server stores it as sent. The screen now rounds each line
  exactly as the server does, so what is shown is what saves. The next purchase
  of the item from the same supplier offers the cost the way it was typed.
- **Checked in headless Chrome** with the sidebar open: no horizontal scroll and
  no clipped field at 1366, 1536 and 1920 px wide. At 1280 px with the sidebar
  open the table scrolls ~80 px sideways inside its own box (nothing clips);
  collapsing the sidebar makes it fit.
- **The item suggestion list now floats over the page** (a portal placed
  against the search box), so the table's scroll box can no longer cut it off.
  It opens upwards when there is no room below.
- **Profit % is gone from the screen.** The owner types the selling price.
  Picking an existing item starts from the price set on its last purchase, or
  its current price. "Below cost" still warns when the price before GST is under
  the cost, without showing a percentage.
- **Profit % is stored per purchase line** (`purchase_items.profit_percent`,
  with `selling_price`), computed by the server on save. It appears only in
  Reports → Purchase items CSV, as *Selling Price (incl. GST)* and *Profit %*.
  That CSV also gained the IGST %/amount columns, which it was missing. Older
  purchase lines are backfilled on start from their stock batch.
- The Profit column was also removed from Items → *Stock & prices*. The batch
  API still returns cost and margin to admins.
- `items.default_profit_percent` is still written on each purchase but nothing
  on screen uses it now.

### 4.9 Unit price is fixed at billing

Asked for: *in the billing menu, the unit price (after GST) should not be
modified.*

- **Billing shows the unit price read-only**, in the same grey box as HSN and
  unit. Hovering it says where to change it: Items → *Stock & prices*. A line

- **The till sends only item and quantity.** `setPriceOverride`,
  `price_override` and `default_price` are gone from the cart store and

- The "price changed" audit-log note is gone. `bill_items.price_overridden`
  stays for lines written earlier and is 0 on every new line.
- Prices are still changed in two places only: the selling price on a purchase
  line, and *Reprice* on a batch in Items → Stock & prices.

## 5. Database and API changes

All schema changes are **additive, automatic on start, and idempotent**
(`initDb()` in `db/index.ts`). Existing data is not rewritten except by the
backfills below.

**Schema**
- `bills.subtotal_amount REAL NOT NULL DEFAULT 0` — backfilled from `bill_items` where 0.
- New table `customer_credit_entries` (+ indexes on `customer_id, created_at` and `bill_id`) — seeded once from history when the table is empty.
- `customers.name` may now be `''` for a customer known only by shop name (the column is `NOT NULL`, so blank rather than NULL).
- New tables `stock_batches`, `bill_item_batches`, `stock_adjustments` (§4.7). Batches are rebuilt once from purchase history when the table is empty.
- `items.default_profit_percent`; `bill_items.unit_price` (backfilled) and `bill_items.price_overridden`.
- `purchase_items.selling_price` and `purchase_items.profit_percent` (§4.8) — backfilled from each line's stock batch where NULL.

**New endpoints**
- `GET  /api/customers/:id/passbook?from&to&order=asc|desc&limit&offset`
- `GET  /api/customers/:id/credit-entries`
- `POST /api/customers/:id/credit-payments` `{ amount, note? }` — refuses more than is owed
- `GET  /api/items/:id/batches[?all=1]` — FIFO order; cost and margin for admins only
- `POST /api/items/:id/stock-adjustments` `{ quantity (±), reason, unit_cost?, selling_price? }` — admin
- `PUT  /api/stock-batches/:id` `{ selling_price }` — reprice what is left in a batch; admin
- **Google Drive backup** — `server/googleDrive.ts` (plain fetch; OAuth `drive.file` + `openid email`). Every backup (automatic and Backup Now) is gzipped and uploaded to a "Vyapara Billing Backups" Drive folder; automatic ones past `BACKUP_KEEP_DAYS` are deleted there. Refresh token in `google-drive.json` beside the DB (0600, git-ignored), not in the DB. Env: `PUBLIC_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (optional `GOOGLE_REDIRECT_URI`). Routes (admin): `GET /api/backups/google/status`, `POST /api/backups/google/connect` (returns the Google URL; one-time `state`, 10 min), `GET /api/backups/google/callback` (unauthenticated; trusts only that `state`), `POST /api/backups/google/disconnect` (revokes). `POST /api/backups/local` now also returns `drive: { uploaded, name?, error? }`. Settings → Google Drive Backup. Guarded by `tests/google-drive.test.ts` (stand-in Google server). README → *Google Drive backup* has the Google Cloud setup.
- **Quick Bill phone app** — `/m` (full-screen, any signed-in user): customer picker, their usual items and best sellers (`GET /api/quick-items?customer_id`), repeat last order (`GET /api/customers/:id/last-order`), big +/- and keypad, Cash/UPI/Credit, same cart store and save as Billing. Counter print queue: table `print_jobs`; `POST /api/bills` takes `print_at_counter`; `POST /api/bills/:id/print-requests`, `GET /api/print-jobs`, `GET /api/print-jobs/:id`, `POST /api/print-jobs/:id/claim` (marks printed atomically). Print station: `src/components/PrintStation.tsx`, switched on per computer in Settings. Bluetooth receipts: `src/lib/escpos.ts` (ESC/POS) + `src/lib/nativePrinter.ts` → Android plugin `android/app/src/main/java/in/chandanls/pos/BluetoothPrinterPlugin.java`. Android app: Capacitor 8, app id `in.chandanls.pos`, loads `https://pos.chandanls.in/m`; release key `android/vyapara-release.keystore` + `keystore.properties` (git-ignored — back up). Guarded by `tests/quick-bill.test.ts`, `tests/escpos.test.ts`.
- **Security for remote access (Cloudflare Tunnel)** — sign-in throttling uses the visitor's address from `CF-Connecting-IP` (trusted only from loopback), plus a per-account cap on remote failures that never locks out the counter; published demo passwords (`scripts/seed-demo.ts`) are refused from the internet (403 `DEMO_PASSWORD`) and can no longer be set; development mode refuses tunnel traffic (503). Automatic backups (`AUTO_BACKUP_HOURS`, `BACKUP_KEEP_DAYS`, `BACKUP_DIR`, `BACKUP_COPY_DIR`); `GET /api/backups/local/status` reports the schedule and last backup. Unused `@google/genai` removed; `npm audit fix` cleared all critical/high advisories. Guarded by `tests/remote-access.test.ts`. README → *Remote access through a Cloudflare Tunnel*.
- **Stock** — `GET /api/stock` (admin and cashier): every item with quantity, status (`in` / `low` at or under `LOW_STOCK_THRESHOLD` / `out`), next selling price, batch count, value at selling price (and at cost, admins only), units sold in the last 30 days, estimated days left, last purchased / sold. Page: **Stock** (click a row for the Stock & prices panel). Guarded by `tests/stock.test.ts`.
- **Sales credit** — `GET /api/sales-credit` (admin and cashier): customers who owe, most owed first, each with their unpaid credit bills oldest first and 0–30/31–60/61–90/90+ day ageing. Repayments are against the balance, so unpaid bills are derived by settling the oldest credit first (the balance is made up of the newest credit it covers; the oldest of those may be part paid); lines always add up to the balance. Page: **Sales Credit** (Record Payment uses the existing `POST /api/customers/:id/credit-payments`). Guarded by `tests/sales-credit.test.ts`.
- **Purchase payments (purchase credit)** — all admin. A purchase is paid at entry (`POST /api/purchases` takes optional `amount_paid`, `payment_method` cash|upi|bank|cheque, `payment_reference`; default 0 = on credit) or later. New tables `supplier_payments` (one row per payment: amount, `paid_on` day, optional method/reference/note, who) and `supplier_payment_allocations` (which purchases each payment settled). What a purchase owes = total − its allocations; nothing else stores it. `purchases.supplier_id` added and backfilled by name. On upgrade every existing purchase is marked paid with one "Paid before purchase payments were tracked" payment (owner's decision). Endpoints: `GET /api/purchase-credit` (owed, by supplier, oldest invoice first), `GET /api/paid-purchases?from&to&search` (fully paid), `GET /api/supplier-payments?from&to&supplier_id` (payment register), `POST /api/supplier-payments` `{ supplier_id | purchase_id, amount, paid_on?, method?, reference?, note? }` (without `purchase_id` clears the oldest invoices first; refuses more than owed or a future date), `DELETE /api/supplier-payments/:id` (undo a mistaken payment). `GET /api/suppliers` adds `amount_due`; `/api/analytics` adds `supplierDue`. Pages: **Purchase Credit** and **Payments Done**. Guarded by `tests/supplier-payments.test.ts` and `tests/migration.test.ts`.
- `DELETE /api/bills/:id` — admin. Returns every unit to the batch it came from (pre-FIFO bills: a new batch at the latest price), takes the credit off the customer and the sale out of their ledger (later entries' running balances shifted), deletes the bill and its lines, audit-logs it. Refused (400) if the customer has already repaid more than their balance holds. History → bill → *Delete Bill*. Guarded by `tests/bill-delete.test.ts`.

**Changed endpoints**
- `POST /api/bills` returns `subtotal_amount` and `tax_amount`; writes a ledger `sale` entry for any credit portion. Prices each line FIFO from batches; refuses (400) a per-line `unit_price` that differs from the batch price (§4.9); accepts an optional `expected_total` (409 `PRICE_CHANGED` on mismatch).
- `POST /api/purchases` requires `selling_price` on every line, creates a batch per line, and stores the line's `selling_price` and computed `profit_percent`.
- `GET /api/reports/purchase-items` rows include `selling_price` and `profit_percent`.
- `POST /api/items` **no longer exists**. A purchase line may carry `new_item: { name, hsn_code, metric }` instead of `item_id`; the item is created in the purchase's transaction, and the response lists `created_items`. `PUT /api/items` takes catalogue fields only; `price` and `stock_quantity` are ignored.
- `GET /api/bills`, `/api/bills/:id`, `/api/reports/sales-items` include `customer_shop_name`; bill search also matches shop name.
- `GET /api/customers` sorts by bakery/shop name; search matches shop, name, phone.
- `POST/PUT /api/customers` require shop name *or* name; balance changes go through the ledger; optional `credit_note` explains an admin adjustment.
- `GET /api/purchases` accepts `from`/`to`.
- `GET /api/analytics` adds `todayBillCount`, `monthBillCount`, `lowStock`, `lowStockThreshold`.

**Environment variables** (documented in `.env.example`): `DB_PATH` (new),
`LOW_STOCK_THRESHOLD` (new, default 10), `AUDIT_LOG_RETENTION_DAYS` (existing, now documented).

## 6. Decisions, and the rules that follow from them

These are the things most likely to be broken by a future change. Each has a
test that will fail if it is.

| Rule | Why | Guarded by |
| --- | --- | --- |
| Bill arithmetic and FIFO allocation live in **one place**, `src/lib/billMath.ts`, used by the server and the cart. Don't copy it. | Prices are GST-inclusive; taxable = line total − rounded taxes; payable floored to whole rupees. Two copies are two ways for the till and ledger to disagree. | `tests/cart-parity.test.ts` |
| The server recomputes every price, tax and total from batches, and refuses any client `unit_price` that differs from the batch price. | A tampered request must not silently under-record a sale, and the owner asked that billing never change a price. | `tests/billing.test.ts`, `tests/fifo.test.ts` |
| `items.stock_quantity` and `items.price` are written **only** by `syncItemStock()` (`db/index.ts`), after a batch change, in the same transaction. Never update them directly. | They are a cache of the batches; any other write lets them drift. | `tests/fifo.test.ts` (stock-adds-up checks) |
| Items are created **only** as new lines of a saved purchase — never by a separate call. | Every item then has a supplier, cost, price and stock behind it; nothing is left over from an abandoned purchase. | `tests/catalogue.test.ts` |
| Stock changes only through purchases, sales and stock adjustments with a reason. | Every movement is traceable; the item form used to overwrite stock silently. | `tests/catalogue.test.ts`, `tests/fifo.test.ts` |
| Any cashier may change a line's price at the counter; it is flagged and audit-logged with the FIFO price. **Confirm this policy with the owner** — restricting it to admins is a small change in `POST /api/bills`. | The request was "I should be able to modify that price". | `tests/fifo.test.ts` |
| Change a customer's balance **only** through `recordCreditChange()`. Never a bare `UPDATE customers SET credit_balance`. | The ledger and the balance must never disagree. | `tests/credit-ledger.test.ts`, `tests/passbook.test.ts` |
| The credit ledger is separate from `audit_logs` and is never pruned. | It is a record of money owed; the audit log is pruned after 400 days. | — |
| A payment can't exceed what is owed; balances never go negative. | The app has no concept of the shop owing a customer (advances). | `tests/credit-ledger.test.ts` |
| Cashiers may record payments; only admins may edit a balance directly or set an opening balance. | Taking money is counter work; writing off debt is not. **Confirm this policy with the owner.** | `tests/catalogue.test.ts`, `tests/credit-ledger.test.ts` |
| The passbook shows each bill once and **excludes** the ledger's `sale` entries. | They are the same money; showing both double-counts. | `tests/passbook.test.ts` |
| Name customers only via `customerDisplayName()` / `CUSTOMER_DISPLAY_SQL`. | Every screen must call a customer the same thing. | `tests/customer-identity.test.ts` |
| Print only via `usePrint`, never `useReactToPrint` directly. | Otherwise printing drops the till out of full screen again. | `tests/fullscreen.test.ts` (the mechanism, not the wiring) |
| Refresh the shared item cache only via `refreshItems()`; list pages keep their own state. | Writing one page of results into the shared cache broke billing search. | — |
| Heavy reads go through `readPool` (worker threads). | `better-sqlite3` is synchronous; a slow query on the main thread stalls every till. | — |
| Schema changes must be additive and idempotent in `initDb()`, with a test in `tests/migration.test.ts`. | The shop upgrades by restarting on its existing `pos.db`. | `tests/migration.test.ts` |

## 8. Known issues, limitations and risks

**Must address before real use**
1. **Demo passwords active** on all three accounts (see top). Also check whether
   the GitHub repo is public; if it is, treat those passwords as public.
2. **`.env` line 23** — leftover token in a comment.
3. **No backup since the schema changes.**
4. **Plain HTTP.** Fine on `HOST=127.0.0.1` (one machine). A second till needs
   an HTTPS reverse proxy — never `HOST=0.0.0.0` on its own.

**Not verified**
5. **No browser testing.** Full screen, print-restore, the passbook page,
   customer forms, cashier management buttons, the FIFO screens (editable bill
   prices, Stock & prices panel), dark-mode appearance — all typecheck and
   build, none has been clicked through. The Purchases table's layout was
   checked in headless Chrome (§4.8); its keyboard flow was not.
6. **Pop-ups may also exit full screen.** The app still uses 34
   `alert`/`confirm`/`prompt` calls (11 on Billing). Chrome may leave full
   screen for these; not confirmed. If it does, replace them with in-app dialogs.

**Functional gaps**
7. **No refunds, returns, voids or credit notes.** A wrong bill cannot be
   corrected in the app; its stock and revenue stand. For GST this likely needs
   proper credit notes.
8. **Credit history before the upgrade is partial** (see §4.3): real sales are
   itemised, earlier repayments appear as one reconciling adjustment.
8a. **No way to correct or delete a purchase.** With batches this matters more:
   a mistyped purchase line can only be fixed with a stock adjustment (to remove
   the quantity) plus a reprice — not by editing the purchase.
8b. **FIFO order is when the purchase was entered**, not the supplier's invoice
   date. Entering last week's invoice after this week's would queue it behind.
8c. **Realised profit isn't reported yet.** The *planned* margin per purchase
   line is in the purchase CSV (§4.8). The cost of every unit actually sold is
   recorded (`bill_item_batches.unit_cost`), but no report uses it yet.
9. **No overpayments/advances** — a payment larger than the balance is refused.
10. No editing or deleting purchases.
11. No admin password recovery in the app. If the admin password is lost, a
    developer has to write a new bcrypt hash into `users.password` and bump
    `token_version`.

**Scale limits** (fine for this shop today)
12. The till's item cache holds 1000 items. The billing **search box** falls
    back to the server beyond that, but the **barcode scanner does not** — a
    scan of an item outside the first 1000 (alphabetically) does nothing.
13. The billing customer picker loads 1000 customers; beyond that, not reachable from the picker.

**Operational**
14. Backups are manual only (Settings → Local Disk Backup).
15. Login lockout counters are in memory (reset on restart); session tokens are in `localStorage`.
16. The front end ships as one 1.46 MB chunk.

**Cosmetic / cleanup**
17. Brand spelled two ways: sidebar "VyparPOS", settings "Vyapara Bakery Supplies".
18. ~~Unused dependencies and AI Studio leftovers~~ — removed (13 Oct 2026): `@google/genai`, `date-fns`, `autoprefixer`, `metadata.json`, the `DISABLE_HMR` block, the obsolete `scripts/repair-bill-rounding.ts` (all bills reconcile; it wrote balances outside the credit ledger), unused imports/exports, and Capacitor's default splash/icon images.
19. Before settings load, the app briefly holds placeholder shop details (`defaultShopSettings` in `useDataStore.ts`).

## 10. Troubleshooting

- **Tests suddenly take 10+ minutes** — leftover server processes from an
  interrupted run are competing for CPU: `pkill -f "tsx server.ts"`. (This
  happened once in this session; it was not a code regression.)
- **`better-sqlite3` fails to load after a Node upgrade** — `npm rebuild better-sqlite3`.
- **Everyone is logged out after a restart** — `JWT_SECRET` changed or is unset.
- **"Too many failed sign-in attempts"** — wait 15 minutes, or restart the server.
- **A customer's balance looks wrong** — open their passbook; every line shows
  billed, received and the running balance, and the credit ledger
  (`GET /api/customers/:id/credit-entries`) shows who changed it and why.
